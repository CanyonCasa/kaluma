## 1. Context

[Kaluma](https://kalumajs.org/) is a tiny JavaScript runtime for the RP2040 and
RP2350, powered by JerryScript, with support for RP2 PIO (Programmable I/O)
assembly embedded in JavaScript. The upstream project is currently **dormant**,
so several open bug reports and build blockers were left unfixed. This fork takes
on the task of evaluating and fixing the bugs, restoring the build, adding full
RP2350 (Pico 2) support, and shipping working firmware.

All 33 open issues in the upstream repository were triaged. Five were actionable
code-level bugs (fixed), and two (#687, #692) were analysed but intentionally left
as follow-ups (see §6). Additionally, the build system had regressed to the point
where **no board could be compiled** under a modern GCC toolchain, and RP2350
support was incomplete (only two of three PIO blocks were reachable).

Bumped from `1.3.0-beta.2` → **`1.5.0`** in `CMakeLists.txt` as part of this

### 2.1 #688 — `ASM.delay()` bounds checking

**Root cause.** `delay(val)` computed `c |= val << 8` with no validation. The
delay field shares the same 5-bit field (bits 8–12) with the sideset value:
sideset occupies the upper bits, delay the lower bits. An out-of-range `val`
bleeds into the sideset bits and corrupts the encoded instruction.

**Fix.** Added a `_maxDelay()` helper that computes the maximum valid delay for
the current sideset configuration (mirroring pico-sdk's
`pio_encode_delay` / `pio_encode_sideset` layout), and `delay()` now rejects:

- non-numeric values,
- fractional values (a hardware delay must be an integer number of cycles),
- negative values,
- values exceeding the delay bits left over after sideset.

### 2.2 #689 — `ASM` program size limit

**Root cause.** `ASM` had no cap on the number of instructions; a program longer
than 32 instructions would be truncated by the hardware.

**Fix.** Added a `check()` method that throws a `RangeError` once the program
exceeds 32 instructions (the RP2040/Pico 2 PIO capacity). Every one of the 9
instruction methods (`set`, `wait`, `in`, `out`, `push`, `pull`, `mov`, `irq`,
`nop`/delegating helpers) now ends in `return this.check();`, so an oversized
program fails fast at assembly time instead of failing obscurely on the board.

### 2.3 #690 + #691 — PIO state-machine teardown & instruction-memory clear

**Root cause.** Neither state machines nor the PIO instruction memory were ever
released or cleared between program runs. On the hardware this means:
- state machines created by one program kept running after it ended (#690), and
- the instruction memory was not reclaimable, so each subsequent `.load` was
  assigned a lower and lower offset until `pio_add_program` could not place the
  program (#691).

The code base already had a `km_pio_init()` (called only at boot) that cleared the
instruction memory and unclaimed state machines — but it was never re-run on
program end.

**Fix.** Added `km_pio_cleanup()` in `targets/rp2/src/system.c` that iterates over
**all** `KALUMA_PIO_NUM` PIO blocks (2 on RP2040, 3 on RP2350):
- disables every state machine (`pio_sm_set_enabled(…, false)`),
- unclaims any claimed state machine (`pio_sm_unclaim`),
- clears the instruction memory (`pio_clear_instruction_memory`).

It is called at the start of `km_system_cleanup()`, which is the single path every
program-end routes through (`.load`, `.reset`, `CTRL+D` soft reset, and program
termination). Each newly loaded program therefore always starts from a clean PIO
state.

### 2.4 #686 — `.help` de-duplication + `CTRL+Z` documentation

**Root cause.** `km_repl_register_command()` appended a new entry on every call,
and modules (e.g. the `fs` module) re-register their dot-commands on every program
run, producing many duplicate lines in `.help`. The `CTRL+Z` shortcut (exit shell)
was also missing.

**Fix.**
- `km_repl_register_command()` is now **idempotent**: if a command with the same
  name is already registered, the re-registration is skipped.
- Added a `CTRL+Z  Exit shell (kaluma --shell)` line to the `.help` output,
  matching the kaluma CLI shell behaviour.

### 2.5 Build fix — modern GCC toolchain support

**Root cause.** The project's build did not work under GCC ≥ 13 (the current
`arm-none-eabi` toolchain). Two independent issues:

1. **JerryScript 3.0.0** fails to compile because GCC 13+ promotes the
   `-Wunterminated-string-initialization` warning to an error. JerryScript's day
   and month name buffers (e.g. `char day_names_p[7][3]`) are intentionally
   fixed-width and trigger the new diagnostic.

2. **pico-sdk's `pioasm`** host C++ tool (built by the CYW43 WiFi driver for the
   `-w` boards) uses `uint8_t`/`uint16_t` without `#include <cstdint>`.
   GCC 13+ `libstdc++` no longer provides these transitively, so the build
   fails with `uint8_t does not name a type`.

**Fix.**
- `tools/kaluma.cmake`: add `-Wno-unterminated-string-initialization` to both the
  host-codegen JerryScript build and the cross-compilation `JERRY_ARGS`.
- `targets/rp2/target.cmake`: an **idempotent configure-time patch** that prepends
  `#include <cstdint>` to the 5 affected `pioasm` translation units in both
  `lib/pico-sdk` and `lib/pico-sdk-2.0.0`. This is done at CMake configure time
  (not by editing the submodules) so a fresh clone still builds; the submodule
  gitlinks remain pinned to upstream.

### 2.6 Board targets — re-enable `pico` and `pico-w`

**Root cause.** `pico` and `pico-w` had been disabled with a `FATAL_ERROR`
("unsupported board") during the 1.3.0-beta transition. The architecture,
CYW43/lwip, and board-configuration wiring was already in place — only the
`PICO_BOARD` mapping was missing.

**Fix.** Added `PICO_BOARD pico` and `PICO_BOARD pico_w` mappings in
`targets/rp2/target.cmake`, removing the `FATAL_ERROR`.

### 2.7 RP2350 (Pico 2) — correct PIO block count

**Root cause.** `KALUMA_PIO_NUM` was set to **2** on both `pico2` and `pico2-w`
boards (copied from the RP2040 headers). The RP2350 has **3** PIO blocks
(`pio0`, `pio1`, `pio2`). `KALUMA_PIO_SM_NUM` correctly stays at **4** (both
chips have 4 state machines per block).

**Fix.** Changed `KALUMA_PIO_NUM` from 2 → 3 in:
- `targets/rp2/boards/pico2/board.h` (line 85)
- `targets/rp2/boards/pico2-w/board.h` (line 86)

### 2.8 RP2350 (Pico 2) — full `pio2` support in the C runtime

**Root cause.** Even with `KALUMA_PIO_NUM` fixed to 3, the C-level PIO code
hardcoded `pio0` and `pio1` in three places, making block index 2 unreachable
on the Pico 2. Passing `pio = 2` to `rp2.pio_sm_irq()` would additionally index
`__pio_call_back[]` out of bounds (the array size was `KALUMA_PIO_NUM`, but the
lookup was hardcoded to only accept 0 and 1).

**Fix.** Replaced all hardcoded `pio0`/`pio1` references with index-driven
lookups using the pico-sdk `pio_get_instance(index)` helper, guarded by
`NUM_PIOS` (which is 2 on RP2040, 3 on RP2350):

**`src/modules/rp2/module_rp2.c`:**
- `__pio(idx)` now returns `pio_get_instance(idx)` (bounds-guarded against
  `NUM_PIOS`), instead of the `if/else` that only accepted 0 and 1.
- Replaced the duplicated `__pio0_irq_0_handler` / `__pio1_irq_0_handler` with a
  single `__pio_irq_dispatch()` plus thin per-block trampolines. The `__pio2`
  trampoline is only compiled when `NUM_PIOS > 2`.
- Added an `__pio_irq_num[]` table (`PIO0_IRQ_0` / `PIO1_IRQ_0` / `PIO2_IRQ_0`)
  sized to `NUM_PIOS`; IRQ enable (`pio_sm_irq_fn`) and handler registration
  (`module_rp2_init`) now iterate over it instead of hardcoding
  `PIO0_IRQ_0`/`PIO1_IRQ_0`.
- Added a bounds check in `pio_sm_irq_fn` — previously `pio >= 2` would index
  the callback array out of bounds.

**`targets/rp2/src/system.c`:**
- `km_pio_init()` and `km_pio_cleanup()` now loop over all `KALUMA_PIO_NUM`
  blocks via `pio_get_instance(b)` instead of only touching `pio0`/`pio1`, so
  block 2's state machines and instruction memory are properly initialized and
  torn down.

**Verification.** All four boards compiled and linked cleanly. ELF symbol check
confirmed: `__pio2_irq_0_handler` is **present** in `pico2`/`pico2-w` and
**absent** from `pico`/`pico-w`, as expected for each chip.
